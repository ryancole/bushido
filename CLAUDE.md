# bushido

Side-view 3D sword PvP game (1v1). C++20, Vulkan 1.3 (dynamic rendering, sync2), GLFW, vk-bootstrap, GLM, Jolt Physics, miniaudio, Dear ImGui, toml++. Dependencies come in via CMake FetchContent; the Vulkan SDK is installed at `C:\VulkanSDK\1.4.350.0`.

## Build (Windows, MSVC + Ninja)

The toolchain is pinned to MSVC via CMakePresets.json (`msvc-debug` → `build/`, `msvc-release` → `build-release/`); CMakeLists errors out on any other Windows compiler. MSVC is not on PATH; chain through vcvars64:

```
cmd /s /c '"C:\Program Files\Microsoft Visual Studio\18\Community\VC\Auxiliary\Build\vcvars64.bat" && cmake --preset msvc-debug && cmake --build --preset msvc-debug'
```

**A build for someone else** is the `package` target, not the build directory — that is hundreds of megabytes of intermediates, and the exe in it leans on absolute paths that exist only here:

```
cmd /s /c '"C:\Program Files\Microsoft Visual Studio\18\Community\VC\Auxiliary\Build\vcvars64.bat" && cmake --preset msvc-release -DSTEAM_SDK_DIR="<sdk>" && cmake --build --preset msvc-release --target package'
```

(Through vcvars64 like every other build here — a bare `cmake --preset` finds no `cl` and fails with "The CXX compiler identification is unknown".)

That assembles `build-release/dist` (~11 MB: exe, `shaders/`, `assets/`, the MSVC runtime DLLs, and with the SDK also `steam_api64.dll` and `steam_appid.txt`), which is the folder to zip. It has been checked by copying it elsewhere and running it: both roots resolve to the packaged copies. The runtime travels with it (`InstallRequiredSystemLibraries`, app-local deployment, which Microsoft permits for the *release* runtime), so the recipient installs nothing — they need only a Vulkan-capable driver, plus the Steam client running for online play. The overlay's invite button additionally requires the game to be launched *through* Steam; reading a SteamID out works regardless.

**Check `CMAKE_BUILD_TYPE` is actually `Release` before shipping anything.** A `build-release` directory holding a stale Debug cache builds the `package` target perfectly happily and produces an exe linked against `MSVCP140D.dll`/`ucrtbased.dll` — the debug CRT, which may not be redistributed and does not exist on a machine without Visual Studio, so it fails to start with no useful message. Nothing in the build output says so, which is why the target now prints a warning when packaged from a non-Release cache. It cost an afternoon once; `dumpbin /dependents` on the packaged exe is the two-second confirmation (a `D` suffix on the runtime DLLs is the tell).

Run: `build\bushido.exe`. Three developer flags drive the determinism harness (`src/netplay/replay.hpp`): `--record <file>` logs every match played this run, `--replay <file>` skips the front end and re-runs a recording, checking the sim's checksum every step (a bare name lands in **`replays/`**, created on demand and gitignored — recordings used to drop into whatever directory the game was run from, which for the standing test below is the repo root, where a `.bsdr` reads as a stray new source file; a name that already carries a directory, or is absolute, is honoured exactly as typed. `replayPath` in `netplay/replay.hpp` is the single rule both ends go through, which is what keeps `--record run.bsdr` / `--replay run.bsdr` a matching pair), and `--auto` skips the front end to play a fixed pairing on Hanami and quit when it ends. It opens with **both fighters walking right for 3 s** (`kAutoOpeningSteps` in main): the left spawn sits three meters off Hanami's stream, and a fight that drifts into the water ends with somebody wedged in the current — a match the bot cannot finish, which since the clock exists runs the full 99 s rather than hanging, but is still a soak run spent watching a body float. The walk is an ordinary input through `stepInput`, quantized, recorded and transmitted like any other, so it costs the harness nothing. `--auto` seeds the rng from a constant, so it's a fixture rather than a play session — two `--record ... --auto` runs produce **byte-identical** recordings, which is a whole-pipeline check that replaying one run isn't. **Caveat, and it has bitten:** a *local* `--auto` run leaves `matchSources` at `{Local0, Bot}` — the bot-drives-my-fighter substitution only applies in a netplay session (main.cpp's `matchSources[mine] = autoMatch ? Bot : Local0`) — so fighter 0 is still reading the live keyboard and mouse, and with sticky input modes on, one stray keypress or click reaching the window perturbs the run. That failure looks alarming and isn't a sim bug: diffing the two recordings shows the first difference in fighter 0's *input* bits with every prior step matching inputs **and** checksum, which is exactly the signature of an external input rather than a divergence. Making the fixture hermetic needs a second `Bot` instance so both slots can be bot-driven locally; until then, don't touch the keyboard while it runs. The standing test:

```
build\bushido.exe --record run.bsdr --auto
build\bushido.exe --replay run.bsdr
```

Netplay is reachable from the menu as **two** entries — **Online (Steam)**, which shows *your* SteamID to read out and takes a friend's, and **Online (Direct)**, which asks for a port or an address — so the flags are only a shortcut past that one screen — and they imply direct IP, so this pair still means what it always did: `--host <port>` and `--join <host:port>` open the socket and drop straight into the fighter picking, which both players still do for themselves. Direct-IP only — LAN or a forwarded port, no NAT traversal. Alongside netplay, `--auto` means "let the bot drive my fighter", which is sound rather than a hack — the bot is an input source like any other, its choices are scheduled and sent exactly as a human's would be — and is the only way to soak-test the protocol without two people. In a netplay session `--auto` also **asks for a rematch instead of quitting** when a match ends — quitting would strand a peer who wanted another round, and an endless run of matches is the more useful shape for the thing `--auto` exists to do (two bot-driven peers will churn through a match every ~10 s indefinitely, which is the cheapest desync soak available). Recording **both** peers is the standing correctness test, since two machines that truly agreed wrote the same inputs and the same checksums every frame:

```
build\bushido.exe --host 7777 --auto --record host.bsdr
build\bushido.exe --join 127.0.0.1:7777 --auto --record client.bsdr
```

The two files must come out byte-identical. Note that two Vulkan windows on one GPU throttle each other badly, so a same-machine test runs the match in slow motion and piles up stalls on the faster peer; that is the test rig, not the protocol.

`--netsim <latencyMs[,jitterMs[,loss%]]>` puts a deliberately worse link in front of the socket (`src/netplay/simlink.hpp`) and `--delay <frames>` sets the input delay, which together answer the question loopback testing cannot: **how much buffer does a real connection need?** Measured with two bot peers, ~35 s each, reporting stalled steps per simulated frame:

| link (one-way, jitter, loss) | round trip | delay 3 | delay 6 | delay 10 | delay 16 | delay 26 |
|---|---|---|---|---|---|---|
| loopback | ~0 ms | 0.00 | | 0.00 | | |
| `20,4,0` | 40 ms | **1.85** | 0.27 | 0.01 | | |
| `40,8,1` | 80 ms | **~3** | | 0.02 | 0.01 | |
| `80,15,2` | 160 ms | | | | | 0.02 |

A fixed 3 frames is a **LAN** figure and degrades badly rather than gracefully — at 40 ms round trip it stalls nearly twice per simulated frame, which shows up as the whole match running in slow motion rather than as anything that looks like a network fault. So the delay is **measured and chosen, not configured**: `--delay` now *pins* it, and the default is to adapt. Every input packet carries the sender's clock and echoes the newest value it has seen from the peer, so each side measures a round trip against its own clock alone — no synchronisation, no agreement about what time it is — smoothed the RTP way into a running mean and mean deviation. `targetDelay()` covers `rtt + 2·deviation`, rounds up, and adds a single frame of slack; **no more than that**, because the measurement already includes the send granularity (the echo comes back through the peer's render loop, which alone reads as ~10 ms of round trip on loopback), and every extra frame is 8.3 ms of lag charged to the player. What it picks, on the same links:

| link | round trip | measured RTT | chosen delay | stalls/frame |
|---|---|---|---|---|
| loopback | ~0 ms | 9 ms | 4 | 0.00 |
| `20,4,0` | 40 ms | 57 ms | 12 | 0.01 |
| `40,8,1` | 80 ms | 100 ms | 17 | 0.01 |
| `80,15,2` | 160 ms | 167–176 ms | 28 / 31 | 0.02 |

Two properties make this simpler than it looks. **Input delay is purely local** — each peer schedules its own input and both still simulate frame F with both inputs — so the two sides need not agree on it and cannot desync over it, which is why the 160 ms row shows one peer at 28 and the other at 31 with no ill effect. And the adjustment is **one-way within a match**: `widenDelay` only ever raises it, filling the new gap by repeating the newest scheduled input, because lowering would mean unsending frames the peer may already hold. A degrading link is answered immediately; an improving one takes the benefit at the next match, where `beginRematch` is free to lower it since nothing is scheduled across the boundary. `Session::stop` reports the ratio, the delay, and the measured RTT, and says so if stalls exceeded a quarter of frames. In-match, `drawNetStatus` puts the same numbers on screen between the blood bars — round trip and delay, cream while the link is fine, amber past a 5% stall rate, red and captioned STALLING past 25%. Those numbers previously existed only in a line printed at exit, which is no use at all to the person wondering mid-match why their swings feel late: a link short of buffer reads as the whole fight running thick, and nothing said so. `Session::stallRate` is a smoothed per-step-attempt rate so the readout describes the connection rather than the last frame, and `waiting()` deliberately excludes a momentary stall — on a bad link that is most frames, and a banner flashing on and off would be worse than useless.

Opens on a loading screen (a real progress bar over the startup work — see `src/main.cpp`), then a main menu (Play / Local Versus / Online (Steam) / Online (Direct) / Options / Quit, mouse or ImGui keyboard nav); Options is the settings screen — a tab per section, currently Controls 1, Controls 2 and Audio (see `src/config`); **Local Versus** is the same match with the second fighter driven by a second person at the same keyboard instead of the bot, set up by running the select screen once per human (player 1 picks fighter, blade and battleground, then hands over; player 2 picks fighter and blade, and *their blade click starts the match* since the ground is already settled); Play opens a character-select screen (mouse-driven, three stages: hovering a tile previews stats, clicking a fighter opens the weapon row (whose panel also names the blade's **stance**, since none of its three bars says anything about the shape of its swing), clicking a blade opens the battleground row, clicking a level locks everything and starts the match against a randomly drawn opponent — fighter and weapon both random; the level is the player's pick). Esc backs out one level (match → menu, select stage → previous stage → menu, options → menu, a pending rebind → cancelled, menu → quit). In a match — the **default** controls are WASD to move in the ground plane (W/S = depth), Space to jump, holding **Left Shift sprints** (break stance and run — or, with both legs cut off, roll the body along the ground; one control, since a fighter with no legs cannot run and one with legs has nothing to roll for, and a fighter down to **one** leg does neither: they stay on their feet and hop, which is slower than a walk and is why the control does nothing for them — see `src/game`), holding **Q blocks** (guard up, slower walk; it used to be Left Shift, which the sprint took), holding **Left Ctrl crouches** (smaller profile, slower walk, no jumping, swings ride a lower lane), the mouse attacks: **left-tap = normal swing, left hold-and-release = heavy swing, right press = quick jab**, and **E throws the blade down — or takes up whatever is lying at your feet**. Every one of those is rebindable to any key or mouse button on the Options screen; the opponent is bot-driven (see `src/bot`). A duel is on a **99-second clock** (`Game::kMatchTimeLimit`, counted down on screen between the blood bars): a match that cannot end is a hang rather than a stalemate — a fighter wedged in Hanami's stream, one who threw their sword away and will not go back for it — and when the clock runs out the match goes to whoever is in better shape (blood, then limbs still attached), which the win overlay calls being *left standing* rather than taking the duel.

VS Code: `.vscode/` has a default build task (Ctrl+Shift+B), a `configure` task, and F5 debug configs (`cppvsdbg`). IntelliSense reads `build/compile_commands.json`.

## Layout

- `src/main.cpp` — game loop (fixed 120 Hz timestep), input reading, scene drawing. Owns the `AppState` machine (`Loading` → `Title` → `Menu` → `Options` | `CharacterSelect` → `Playing`, Esc backs out one level — during `Loading` it just quits, since the menu can't be entered half-built, and during `Title` it skips to the menu, which is where the sequence was going anyway): **Loading** is the state the app opens in, and it's a genuine progress screen rather than a splash on a timer — a `LoadStep` table (label, weight, thunk) holds everything that has to happen before the menu comes up, and the loop runs **exactly one step per frame**, so the window keeps pumping events and the bar advances on real completions. The steps are the work that used to stall inside constructors: opening the audio device, loading the settings, synthesizing the effects, decoding the menu theme's WAV (`Audio`'s staged init — see below; a battleground's theme is *not* here, it loads with its match), building the voice pools, prewarming every level's cached static geometry, and constructing the diorama `Game` (which boots Jolt). `weight` is the step's **measured** cost in ms (debug build) because the steps are wildly uneven — opening the device costs more than everything else together, a level prewarm rounds to nothing — so a bar driven by step count would sit still and then leap; the numbers only need to hold their ratios. A step runs *after* the frame naming it is presented, so the label on screen is the work being waited on, and the drawn fill eases toward the true fraction (it only ever chases real completions, so it can't run ahead of the work — and on a fast machine a ~300 ms load reads as one sweep instead of a single frame at 100%). `game` is null until the last step, which is what the loading branch's early `continue` protects. Then: menus freeze the sim (accumulator zeroed) but keep drawing the arena behind the UI; ImGui menu code (`setupMenuStyle`/`drawMainMenu`/`drawOptions`/`drawCharacterSelect` — restyled colors, Georgia from the system fonts when present, per-widget sizing via `ImGui::PushFont(nullptr, size)`) lives here, built between `beginFrame`/`endFrame`. The select screen is single-player and mouse-driven: a tile row where hovering previews a character's stats in the panel below (crimson frame follows the preview) and clicking picks it; the opponent's roster index is drawn at random (`std::mt19937` in main). `Game` is heap-owned and **rebuilt from the two (character, weapon) index pairs on pick** — every match starts fresh; the initial instance is just the diorama behind the menu. Input reading itself lives in `src/input.hpp/.cpp` (see below); main holds the wiring: a `matchSources[2]` of `InputSource` beside the loadout indices saying who drives each fighter, one `LocalInput` latch per local control set, and a `localKeys` lambda naming which `Settings::keybinds` set a local slot reads. The fixed-step loop dispatches on `matchSources` rather than assuming player 2 is the bot: locals hand over the frame's latched input, the bot is asked per step (it reads state the last step moved, and stands down once `Game::over()`), and `Remote` means the `Session` supplies both fighters' inputs for the frame — or none, and the loop breaks, because a lockstep stall is the whole sim waiting. `SetupMode` (`Solo`, `LocalVersus`, `NetHost`, `NetClient`) is chosen when a flow starts and read once the select screen finishes — the one place the four modes differ. `AppState::NetSetup` is `drawNetSetup`, the host-a-port-or-join-an-address screen; opening the socket is deliberately done *there*, where a bad port or address can still be corrected, rather than after someone has picked a fighter, and its hint line doubles as the error line. There are **two** menu entries into it and the choice is the player's: `MenuAction::OnlineSteam` and `OnlineDirect` set `netSteam`, which is what the screen draws and what `bindLink` binds the session's `Transport` to. That split replaced a single **Online** whose fields depended on whether Steam had come up at launch — which is unreadable from the outside, since a build with the SDK and a dead Steam client look identical from the menu, and it meant a player could not *ask* for Steam. So the Steam screen now draws with no Steam behind it: `selfId` is 0, the fields and both buttons are `BeginDisabled`, a **Retry** appears in their place, and `steamStatus` says in red why (Steam's own words, via `SteamAPI_InitEx`). The two states worth keeping apart are `steamUp` — the API answered, which is what decides whether the relay can carry a match and whether the lobby callbacks are worth pumping — and `netSteam`, which screen the player asked for; a Steam invite arriving on the direct screen sets the latter and rebinds, since an invite chooses a transport as much as an opponent. `AppState::NetWait` is where **both** roles wait out the handshake, since neither can build a `Game` until the merge settles which fighters are in it. A netplay client drives fighter **2** with its own player-1 controls (its only keyboard), which is why `drawWinOverlay` takes the local slot rather than assuming 0, and why the `matchSources` assignment is written in terms of `session.localSlot()` instead of a fixed pair. `session.pump` runs on the *render* frame, not the fixed step: packets have to keep flowing during a stall, since ours are exactly what the peer is waiting for. The accumulator is capped at 8 steps in a netplay match so a long stall can't bank time and then teleport through the backlog. `startMatch` (shared by pick and rematch) re-seeds every latch and re-brains the bot from whichever slot claims it. Nothing polls a hardcoded `GLFW_KEY_*` except Esc, which is deliberately unbindable. The select screen is also what sets up a **local versus** and both ends of a netplay match: `SelectScreen::player`/`mode`/`pickLevel` say who is picking and what their last click leads to. It carries the whole `SetupMode` rather than a `versus` bool because the hint line has to stay honest — a netplay host's opponent is not "drawn at random", they are a person still choosing, `beginSelect(versus, player)` opens a pass, and main's `versusSetup`/`selectingPlayer` remember that a second one is owed. Player 2 inherits the ground, so their blade click is the one that starts the match. The *only* difference between the two modes at the end is who drives slot 1 — `InputSource::Local1` or `InputSource::Bot`; the random opponent draw is skipped when a human picked. Esc during player 2's pass abandons the whole setup back to the menu rather than rewinding to player 1. `drawOptions` is the settings screen: an `OptionsSection` tab row (one per `Settings` member — adding a group of settings is a struct there plus a tab here) over a **fixed-size** content child, since the window is centered and auto-sized and would otherwise jump on every tab click. `sectionKeybinds` maps a section to the control set it edits (or null for Audio), which is what makes Controls 1 and Controls 2 one code path. A controls section is a row per `Action` whose button shows the current control and, when clicked, waits for the next one; capture **polls** `pollAnyBind` rather than installing a GLFW key callback (ImGui's backend owns those, `install_callbacks = true`), which also makes the table the validity filter, and two latches on `OptionsScreen` (`armed`, `swallow`, the latter cleared *after* the widgets since ImGui fires buttons on mouse release) keep the clicks that open and close a capture from being read as the binding. A control already in use **trades places** with the row being edited, so every action stays bound and there's no unbound state to render or save — and the sweep covers **both** control sets, not just the edited one, because in a versus they're live together and a control shared across sets would move both fighters with no click able to fix it. For the same reason a section-scoped `Defaults` that would re-claim a control the other set was moved onto resets both (the two default sets are disjoint, so that always lands somewhere valid). The Audio section is a percent slider per level: moving one applies to the mixer that frame (`OptionsResult::applyAudio` — the menu theme is playing, so music previews itself) but only persists on `IsItemDeactivatedAfterEdit`, otherwise one drag across the slider would be a hundred file writes; releasing the SFX slider also fires a one-shot `Sfx::Hit` (`previewSfx`), since nothing in a menu would otherwise make the level audible. `Defaults` is **section-scoped**, so resetting the controls can't quietly move the volumes. There's no apply step anywhere — edits land in `settings` live and the caller just persists them. In-match HUD: `drawBloodBars` paints a blood bar per fighter into the foreground draw list (top corners, draining outward) and names the blade **currently in hand** rather than the one picked, since it can change hands or be thrown away mid-match; `drawMatchClock` puts the countdown top centre, cream until fifteen seconds and crimson under five, on screen for exactly the reason `drawNetStatus` is — a match can now end without anybody dying, and a duel that stops on its own with nothing having said why reads as a bug (`drawNetStatus` moved down to sit under it). When `Game::over()`, the bot's input is zeroed (the human keeps control) and after a 1.2 s beat `drawWinOverlay` shows Rematch (same pairing *and* the same input sources, fresh `Game`) and Character Select buttons over VICTORY/SLAIN — or PLAYER 1/2 WINS in a versus, since "VICTORY" would be true for exactly one of the two people reading it. Across a wire the verdict is again the reader's own (hence the local-slot argument, a client being fighter 2), the buttons are Rematch, Change Fighters and Disconnect, and the first two are *requests*: clicking either swaps them for "waiting for your opponent..." until the other side asks for the same thing. Under `--auto` a bot peer mirrors whatever intent the human asked for (and re-submits its existing loadout on a reselect, having nobody to pick for it), so one driven window is enough to exercise both agreements.
- `src/config.hpp/.cpp` — player settings, persisted as TOML at `%APPDATA%\bushido\bushido.toml` (cwd if `APPDATA` is unset). `Settings` is the root and the whole of what the file holds — **one struct per options-screen section**, so a new section is a struct here, a `[table]` in the file, and a tab in `drawOptions`. Current three: `keybinds`, `keybinds2` and `audio`. The two control sets are one per local fighter (`[keybinds]` and `[keybinds_p2]`), and their defaults **share no control** — player 1 keeps WASD and the mouse, player 2 gets the arrows plus the `, . /` cluster and the right-hand modifiers (deliberately not the keypad, which half of laptops don't have). That disjointness is load-bearing rather than tidy: in a local versus both sets are live at once, so an overlap moves both fighters on one key (`AudioSettings`: `music`/`sfx`, 0..1, both defaulting to **1 — the levels everything was synthesized against**, so a fresh install sounds exactly as it always has and the sliders only ever cut; main pushes them into `Audio::setMusicVolume`/`setSfxVolume` at startup and on every edit). A `Bind` is a `{device, code}` pair — keys and mouse buttons are separate GLFW numbering spaces (`GLFW_MOUSE_BUTTON_LEFT` is 0, also a valid key code), so the device travels with the code, and any action can take either. `Action` enumerates the eleven rebindable controls (`Sprint` is **Left Shift** / **Right Shift**, which is where it belongs and which cost block the key it used to sit on — block is now **Q** for player 1 and **Apostrophe** for player 2; `Drop` is **E** for player 1 and **Semicolon** for player 2 — one control for both throwing the blade down and taking one up, since which of the two a press means is never in doubt from where the player is standing, and only the sim knows what is in a fighter's hand); `kBindTable` in the .cpp is the single curated list of bindable controls (name ↔ device+code), which makes `bindName` total, gives `parseBind` its vocabulary, and *is* the options screen's capture set — a control not listed simply can't be bound. **Escape is deliberately absent** from it: it's the hardwired back-out key, so binding it would strand the player mid-match. Names, not integers, go on disk (`crouch = "Left Ctrl"`), so the file survives a GLFW renumber and reads as documentation; the enum order is display order while `actionKey` (`"move_left"`) is the on-disk contract, so rows can be reordered or relabeled freely. Parsing is toml++ (`toml::parse` on an `ifstream`, throwing form). Recovery is layered so a file can always be partially useful: a syntax error leaves every default standing, **each section is read independently** (a file predating `[audio]`, or with a section deleted, keeps that section's defaults and loads the rest), and within a section each entry falls back on its own — a stale control name loses one binding, a level that's out of range is *clamped* rather than dropped (a hand-edited `2` is obvious intent), and an integer `1` is accepted where a float is expected since TOML distinguishes them. A loaded section then gets a **duplicate sweep**, because per-entry recovery isn't enough on its own: a file written before an action existed carries no line for it, so it keeps that action's *current* default — which the file may already have spoken for. Sprint did exactly that, taking the Left Shift every config on disk still names as block, and a shared control is the one state the options screen never lets you reach and no amount of clicking can fix. So the roster is walked in order and anything finding its control claimed falls back to its own default, then to the first free control if that is taken too (logged, and every action still ends up bound). Earlier rows win, which is what lands the migration right: `Sprint` is listed above `Block`, so it keeps the shift and block drops onto the key its default now names. Everything but a *missing* file logs to stderr; a missing file is normal first-run, not an error. Saving is hand-emitted rather than run through toml++'s serializer, which drops comments and sorts keys: a dozen lines are worth a header explaining the file and the roster's own order. Keybinds are local input mapping only — they never reach the sim, so unlike stats they can't desync a future netplay peer.
- `src/input.hpp/.cpp` — turning controls into `PlayerInput`, and saying where each fighter's input comes from. `InputSource` (`Local0`, `Local1`, `Bot`, `Remote`) is a **per-slot** answer to "who drives this fighter": the sim takes two `PlayerInput`s and has no idea which is which, so a match is described by a source per slot instead of "player 2 is the bot" wired into the loop — which is what lets local versus and a netplay peer reuse one dispatch. `localSlot()` maps a source to its latch index, or -1 for the sources that aren't a person at this keyboard. `LocalInput` is that latch, one per local control set: the held controls (move/jump/sprint/block/crouch) are *levels* and are read fresh every render frame, but the attack, jab and drop controls are **edges** — the attack control fires on release (a tap is the light swing, a hold ≥ `kHeavyHoldTime`, 0.28 s, charges the heavy) while jab and drop fire on press — and edges are detected per render frame while being consumed by fixed steps, of which a frame may run **zero**. So a press sits on the latch until a step takes it (`poll` → `current()` → `consumeEdges()`), and `beginMatch` re-seeds from live control state at match start, flagging an already-held attack control suppressed so the click that locked in the battleground can't land as an opening swing on its release (the drop control is seeded the same way, so a key already down at the whistle can't throw the blade away on the opening frame). This was six loose locals in the main loop for as long as exactly one fighter could ever be human. The file also owns the **wire format**: `packInput`/`unpackInput` put a `PlayerInput` in twelve bits (two per movement axis, one per button, two for `AttackKind`, one for drop, one for sprint), which is the replay record and the netplay packet defined **once** so a recorded match and a transmitted one can't drift apart. Bits are only ever **appended**: the packet is a fixed two bytes either way, so widening the meaning of a spare bit costs nothing on the wire and needs no `kReplayVersion`/`kProtocol` bump — an older recording replays with the new bit clear, which is exactly right, since nobody dropped anything, or ran anywhere, in a match played before the control existed. `quantizeAxis` is the contract that goes with it — an input that doesn't survive `packInput` unchanged is one the sim plays and no recording or peer ever sees, so a source that thinks in continuous values quantizes *where it decides* rather than being silently rounded downstream. That is not hypothetical: the bot's depth steering was analog, and it desynced the first replay ever run at step 218.
- `src/netplay/` — the determinism harness, and where the transport will go. `replay.hpp/.cpp`: lockstep and rollback both rest on "two machines fed the same inputs reach the same state", which is either true or the whole approach is worthless, and the only way to know is to check. `MatchSetup` is a match in full — the same five integers `Game`'s ctor takes, and exactly what two peers would agree on before the first step. A recording is that header (28 bytes) plus, per fixed step, both packed inputs and `Game::checksum()` after them (8 bytes a step, flushed as it goes: a recording of the crash you're chasing beats a tidy one you never get — which also means a killed run leaves a valid partial log, and `(size - 28) / 8` is how many steps it got). `replayPath` decides where a name lives (bare ⇒ `kReplayDir`, i.e. `replays/`; anything with a directory in it is taken literally) and **both** `Recorder::open` and `Replayer::open` go through it, since two copies of that rule would eventually disagree and the symptom would be "--replay cannot find what --record just wrote". Every message names the *resolved* file rather than what was typed, now that the two differ. `Replayer` feeds the inputs back and compares every step; `dumpDesync` prints both fighters field by field at the first mismatch and stops there, since everything after is downstream of the same divergence. Replaying on the machine that recorded catches frame-order and uninitialised state; replaying on a *second* machine catches the rest (thread counts, instruction sets, compiler differences). That second half has since been cleared the hard way rather than by replay: a Steam match played through between two machines without the desync check firing, and since a divergence halts the session with a red banner rather than drifting quietly, a match that finishes is the same evidence a matching replay would have been. A log is only meaningful against the build that wrote it: `kReplayVersion` covers the file layout, while a sim change legitimately moves the checksums and reports a desync at step 0. `transport.hpp/.cpp`: a datagram pipe to one peer — unreliable, unordered, no delivery guarantee, which is all lockstep needs since every packet repeats the last several frames and a reliability layer would only add the head-of-line blocking the protocol exists to avoid. `UdpTransport` is direct-IP Winsock (pimpl, same reason Physics hides Jolt), so **LAN or a forwarded port only**. The relay that fixes that is **Valve's infrastructure, not a library**: GameNetworkingSockets is the same API open-sourced, but the standalone build gives transport plumbing only — NAT punch-through still needs signalling and STUN/TURN servers someone has to run. Steam Datagram Relay, reached through `ISteamNetworkingMessages`, is what actually makes "click a friend, play" work without either end touching a router, and it comes from the Steamworks SDK. That is why `SteamTransport` is the second real implementation rather than a GNS one. `steamtransport.hpp/.cpp`: the same `Transport`, addressing a **person** instead of an endpoint — a SteamID, with Valve's relay carrying the packets, so there is no port to forward. Built on `ISteamNetworkingMessages` rather than `ISteamNetworkingSockets`, because connectionless send-to-a-peer is already the shape of `Transport` and the connection-state machine would only be flattened back out; sends are unreliable + `NoNagle`, since every packet the session emits is self-contained and a retransmit could only arrive too late to use. The Steamworks SDK is **licence-gated and cannot be fetched by the build**, so this is opt-in: `-DSTEAM_SDK_DIR=<the sdk directory>` compiles it in, links `steam_api64`, copies the DLL beside the exe, and writes a `steam_appid.txt` (480, Valve's public test app, until the game has an id of its own). Without it the file compiles to a stub whose `available()` answers false and the game still plays over direct IP. `SteamAPI_Init` needs the Steam client running and reads the app id from the **working directory**, so a dev run wants `-WorkingDirectory build`. **Which transport a match uses is chosen at the menu**, not inferred: **Online (Steam)** and **Online (Direct)** are separate entries, and picking Steam gets the Steam screen whether or not Steam is there to answer. It used to be a single **Online** that quietly became one or the other depending on what had initialised at launch, and the failure had no reader anywhere — a friend running a packaged build got the direct-IP screen with nothing on it saying why, which is indistinguishable from a build made without the SDK, and the one stderr line about it goes to a console window nobody reads. So: `SteamAPI_InitEx` (not `SteamAPI_Init`, which collapses every failure into a bare false) gives `SteamTransport::status()` a sentence — "Steam is not running.", "The Steam client is out of date.", or Steam's own words for anything else — and the Steam screen prints it in red with the fields disabled and a **Retry** where the buttons were. Retry matters because the answer used to be taken once at startup and never revisited, so launching the game before the client had finished starting cost the whole run; `bindLink` rebinds the session's `Transport` whenever the answer changes. `--no-steam` and a build without the SDK are still not errors, and the flags still decide it for a run that skips the menu. `--host`/`--join` *without* `--steam` also mean direct IP, since a port and an address are not things Steam has; `--steam` forces the issue and fails rather than falling back, which is what a test run wants. **This path has carried a real match between two machines** — the last mile that could not be checked here. It still **cannot be tested from one machine**, which is measured rather than assumed: both local routes are closed by Steam itself, since messaging your *own* SteamID trips an assertion in `csteamnetworkingmessages.cpp:233` and drops the session, and an IP identity is refused outright ("Bad FakeIP type", result 5003) because `ISteamNetworkingMessages` is SteamID-only. `ISteamNetworkingSockets` *would* connect over IP locally with `IP_AllowWithoutAuth`, but that is a different API from the one this file uses, so a passing test there would prove nothing about this code. So changes here are verifiable locally only as far as "compiles, initialises, hosts"; anything past that needs two machines and two Steam accounts again. `steamlobby.hpp/.cpp` is the matchmaking half — how two people *find* each other, as against how bytes reach one already found, which is why it is not part of `SteamTransport`. Hosting opens a **friends-only lobby with two seats** (an open one would let a stranger take the other side of a duel) and the wait screen offers Steam's own friend picker; whoever joins reads `GetLobbyOwner` and connects to them, so the host still only ever listens. An invite arrives one of two ways and both land in the same place: `GameLobbyJoinRequested_t` if the game is already running, or a `+connect_lobby <id>` argument if Steam had to launch it — the plus is Steam's, not ours. `CreateLobby`/`JoinLobby` answer asynchronously (`CCallResult`, not a plain callback), and `SteamTransport::pump` drives these callbacks too, since `SteamAPI_RunCallbacks` is global. The overlay is **not** assumed: `IsOverlayEnabled` is checked and a refusal says "send them your ID instead" rather than leaving a button that appears to do nothing — which is what happens whenever the exe is launched directly instead of through Steam, so it is the common case during development, not an edge one. Typing a SteamID by hand stays on the Online screen as the path that works regardless. A host adopts the first sender as its opponent and ignores everyone else after that, which is fine for two people who arranged a match and not enough for a public listener. `simlink.hpp/.cpp`: a `Transport` that wraps another one and makes it worse on purpose — one-way delay, jitter, and loss. Every netplay test otherwise runs over loopback, which is the one condition the game will never ship on, and a lockstep protocol's whole character (how much delay it needs, how often it stalls, whether the redundancy window is wide enough) only shows up under a real link. Delay is applied on **receive** rather than send: when both peers simulate, each holds what arrives, so the round trip is twice the one-way figure and there is only one clock to reason about. Jitter is allowed to reorder packets, which is realistic and which the protocol is meant to survive — frames are *indexed*, not sequenced, so a late one is either still useful or already redundant. Deliberately outside the sim: the two peers drop different packets, exactly as two real machines would. It is also the second implementation of `Transport`, which is what makes that interface a demonstrated seam rather than a claimed one. `session.hpp/.cpp`: **delay-based lockstep**. Both machines run the identical sim, so the wire carries *inputs* — two bytes a frame per peer — and never a world. An input sampled now is scheduled `kInputDelay` (3) frames ahead, which is how long the network gets to deliver it, and a frame is simulated only once **both** peers' inputs for it are in hand: a missing remote input is a **stall**, not a guess, so nothing is ever mispredicted and there is nothing to roll back. Every packet repeats the newest `max(kInputRedundancy, inputDelay)` frames, so four consecutive datagrams have to vanish before a stall and nothing is ever retransmitted. That window must **never be narrower than the input delay**: at startup a peer has seeded exactly `inputDelay` frames and sent nothing else, so a 12-frame window with a delay of 16 leaves frames 0–3 untransmitted and both sides wait on frame 0 forever — which is exactly what happened the first time the delay was raised past 12. Ring buffers are indexed by frame mod 256 and the consumed remote slot is cleared on use, so a wrap can't read as "already have it"; frames outside `[m_frame, m_frame + 128)` are dropped so a stale or malformed packet can't scribble on the ring. Handshake: each side passes `start()` only *its own* half of the match — the host fills slots `[0]` and the level, the client fills slots `[1]` — and the two halves are **merged over the wire**, so neither player has a fighter chosen for them. The client's pick rides in on `Hello`, the host merges it and answers `Welcome` with the whole `MatchSetup`, and both then hold the identical thing `Game` is built from. The host answers *every* Hello, since a lost Welcome has to be re-answerable, and there is deliberately no "promote to Running on Inputs" shortcut: a host cannot start without the client's fighter, and cannot miss it either, because a client only sends inputs after a Welcome and a Welcome only follows a Hello. `kProtocol` mismatches are refused at the handshake rather than desyncing ten seconds later. The `kTimeout` silence check is **not** applied to a host still in the handshake: it is advertising, not waiting on anyone in particular, and timing that out means a lobby that quietly dies while you walk to the other machine. A client gets the timeout (its address may simply be wrong, and "could not reach the host" is the useful answer), as does any running match. Each packet also carries the sender's last simulated frame and its `Game::checksum()`, which the peer compares against its own — a mismatch is fatal, loud, and stops the sim rather than letting the two worlds drift apart quietly. **The sim advances at the slower peer's rate**, which is inherent: scheduling a local input requires taking a step, and taking a step requires the other side's input. **What happens after a match** is agreed rather than commanded — one player cannot restart the other's game, nor drag them back to a select screen — and needs no reliability layer, because a request is a *level, not an edge*: each peer's `Intent` (`None`/`Rematch`/`Reselect`) rides on every input packet and repeats until the state changes, so there is no ack to lose and nothing to retransmit. **Reselect** is what keeps two people from having to tear the connection down and redo the whole host-and-join dance just to swap a sword: both go back to the select screen with the session live, and each peer's own half of the next match (`chars[mine]`, `weapons[mine]`, and the level if it is the host) travels on **every** packet — twelve bytes to avoid a second negotiation. That the peer's half is kept from every packet, not only from a "ready" one, is what makes the roll-forward race safe: if they commit before their ready flag reaches us, we still hold the pick they committed with. `beginRematch` folds their half in, so a plain rematch (where nothing changed) and a reselect are the same code path. **The loser names the next battleground** — the host's is the one that counts only on the opening handshake, after which it is whoever lost the last match (`Session::ownsLevel`, set from `submitLoadout`). Both peers work out who that is from the same `Game::winner()`, so they agree without exchanging a word about it, and the winner's select screen simply ends on the blade. Without this the host owned the ground forever and a joining player never got to choose one. When both flags are set, each side independently calls `beginRematch()` and rebuilds the same fresh `Game`; they need not do it on the same frame, since lockstep resynchronises at frame 0 of the new match exactly as it did at the first. Every input packet also carries `m_match`, the index of which match in the session it belongs to, which is what makes packets still in flight from the finished match harmless rather than a source of phantom inputs. The one race — peer A observing agreement, restarting, and so ceasing to advertise the flag before B ever saw it — is closed by `m_peerAhead`: a packet from `m_match + 1` implies agreement, since a peer only rolls forward after seeing *our* request.
- `src/characters/` — the selectable roster, one file per fighter (same shape as `src/levels/`). `character.hpp` is the whole public surface (`CharacterStats`, `CharacterDef`: stable `id` slug, name, `SamuraiColors`, authored 0–5 select-screen ratings, `kCharacterCount`, `characterDef(index)`); `character.cpp` is just the index → def table, whose order is the select-screen order *and* the netplay index, so rows are appended, never reordered; `registry.hpp` declares each fighter's namespace. Each fighter owns one .cpp (`ronin.cpp`, `shinobi.cpp`, `oni.cpp`, `kensei.cpp`) holding its `kDef` in C++20 designated-initializer form plus the design note for what it trades away — a character carries no code of its own today, so a namespace holds nothing but `kDef`; per-fighter hooks (move sets, model tweaks) would go beside it the way `levels/registry.hpp` carries draw/obstacles/water. Adding one: new .cpp, a namespace in `registry.hpp`, a row in `character.cpp`, `kCharacterCount`++. All stats are compile-time constants and a match is fully described by two (character, weapon) index pairs plus a level index — **multiplayer-ready by construction**: peers would only ever exchange indices/ids, never stats, keeping the sim deterministic across machines. Current four: Ronin (baseline — the old global constants), Shinobi (fast/light), Oni (slow, huge knockback, heavy), Kensei (longest reach). Stats: moveSpeed (**slower than a walk**, 0.65–1.05 m/s across the roster, read as individual steps rather than as travel — a hit can end the match outright, so the approach is the whole negotiation and closing the last two meters has to cost enough seconds for the foe to answer it; the Ronin's 0.85 gives about one footfall per second. Sprinting is the way out of that and pays for it in kind — see the sim's **Sprinting**: it is the same stat times `kSprintMoveScale`, bought with the guard, the swing and the body's facing. Movement is **driven by the foot rather than the other way round**: everything falls out of the requirement that a planted foot must not move in world space. It is a **shuffle, not a walk** — a fighter holding a sword never lets their feet cross, and the same leg leads all match. A cycle is two *movements*: the lead foot reaches out, then the rear closes up behind it, reversed when backing off so the rear goes first. Which foot goes first comes from `Player::strideDir`, the travel direction in the fighter's *own* frame — a vector rather than a sign, because a duel is not fought along one axis: the step is taken along it, and the leg's whole swing plane turns onto it (`LegPose::azimuth`), so a side-step is a side-step instead of the fighter sliding in depth on legs doing a forward shuffle. The tie when travel is square to the stance is broken by each leg's own z offset, so a pure side-step leads with the leg on the side being stepped toward. `Game::update` owns only how far a cycle carries the body (`kShuffleStride`) and how the seconds are spread inside it — `2·sin²`, one surge per foot movement, zero while the weight changes feet. That averages to exactly 1, so the mean is precisely the speed stat, and samurai.cpp integrates the *same* curve to place the planted foot: those two being one function is what keeps the foot still. Speed therefore sets cadence alone — a slow fighter shuffles less often, never smaller. `Player::strideBlend` eases the *stepping* in and out (the stance separation is held either way, since a guard is a guard whether or not you are moving in it)), jumpVelocity, windup/active/recovery times, reach (blade tip from shoulder — drives both the gameplay sweep and the drawn blade length via `SamuraiPose::reach`), knockback dealt, weight (divides knockback/pop received).
- `src/levels/` — the battleground roster, one file per level. `level.hpp` is the whole public surface (`LevelDef`, `LevelObstacle`, `LevelWater`, `kLevelCount`, the five `levelX(index)` accessors), same compiled-in-roster contract as characters/weapons; `level.cpp` is nothing but the index → implementation dispatch over a `LevelEntry` table; `registry.hpp` declares each level's namespace (`def` and `draw` required, `obstacles`/`ground`/`water` optional — a null hook means "none", which is why Dojo only fills in two); `scenery.hpp` holds the shared `box`/`hash01` draw helpers. The **sky** is the one thing every level shares the shape of: `SkyDef` (zenith, horizon, and the ground colors, plus a `CloudDef`) is a member of `LevelDef` rather than an optional hook, so a new battleground cannot open onto the bare clear color by forgetting to write one, and `sky.cpp` holds the shell all of them are drawn in — levels differ in weather, not in how a sky is built. That shell is a stack of four-walled rings from the horizon up to a cap, each ring one step along horizon → zenith (16 of them: the camera sits low and its vertical fov is narrow, so only the lowest few bands are ever on screen and the count has to buy resolution *there* — 8 left visible seams behind the Dojo's pillars), plus the same rings below the horizon in the ground color for the land the arena floor sits on. It is drawn **unlit** (see the conventions below) and built around the **eye** rather than around the arena, which is what makes it read as sky: it never gets closer, and since `FramingCamera` pulls back further the narrower the window, a shell pinned to the arena would have to guess how far. Sized to enclose the camera and still fit inside the 200 m far plane from its own center — a corner sits ~180 m out. Inside that shell hangs the **cloud deck**, `drawSky`'s one moving part and the reason it takes `time`: `count` clouds on their own ring around the eye, each a seven-box cluster (a broken base with crowns piled on it, colored between the level's two authored cloud colors by piece — `sunlit` for the crowns, `shaded` for the underside), everything about cloud *i* a pure function of `hash01(i)` and the clock, so there is no stored state and nothing for the sim to know about. Three things are load-bearing. The wind is an **angle** per second, not meters: what a distant cloud does on screen is sweep across, and a deck translated in world units would slide out of the sky and leave a hole behind it — turning the ring instead means it is closed, so nothing ever pops in at an edge and there is no wrap to hide. A cloud's height is authored as an **elevation angle** from the eye rather than a y, which is both what the camera cares about (the frame's top edge is a fixed 25° above the view axis, since the fov never changes) and what a sky at infinity does when the eye rises: hold its angle. And that band is deliberately the **lower** half of the sky (~6°–19°), because a cloud overhead is seen belly-first and a belly made of boxes is a flat plank — the crowns that say "cloud" are all on top, and only a cloud near the horizon shows them. It was drawn at twice this size and twice this high once, and read as a stack of shelves. Near clouds also drift faster than far ones (`ω ∝ 1/radius`, the way anything passing at a fixed speed does), which is the only depth a sky of flat colors gets; the radius band is bounded by the shell it hangs inside, and the low clouds mix toward the level's own `horizon` color so the deck sits in the gradient instead of on top of it. A clear sky is `count` 0 and costs nothing. Each battleground owns one .cpp (`dojo.cpp`, `hanami.cpp`) holding its def, its solid geometry, **and** its drawing together — the scenery is bespoke procedural code, so splitting data from drawing would only fracture a level across two places. Adding one: new .cpp, a namespace in `registry.hpp`, a row in `level.cpp`'s table, `kLevelCount`++. Levels share the arena depth but **author their own width** (`LevelDef::arenaHalfWidth` — Dojo the baseline 12, Hanami widened to 16; `Game` bakes it in as `arenaHalfWidth()` and hands it to `Physics` for side-wall placement); a level contributes scenery plus **solid obstacles**: `levelObstacles(index)` is a deterministic once-built list of `LevelObstacle` boxes (Hanami's bank stones; Dojo has none) that `Game`'s ctor feeds to `Physics` as static colliders *and* `drawLevel` draws from — one list, so what you see is exactly what you collide with (stones near the fighter spawns are skipped at generation). `drawLevel(renderer, index, time)` draws the scenery (called first by main's `drawScene`, so gameplay draws on top), with all ambient motion a pure function of `time` (deterministic `hash01` scattering, no stored state). Current two: Dojo (the original dark slab + pillars — flat, dry, nothing solid) and Hanami (grass banks around a genuinely carved stream at x = −6 — clear of player 1's spawn at −3: `levelGround(index)` replaces the default flat physics slab with per-level boxes (two banks + a 0.35 m-deep bed, under the 0.4 m step-up so fighters wade shin-deep and climb out), and `levelWater(index)` describes the water volume — `Physics::step` gives debris inside it buoyancy + drag toward the 0.55 m/s +z current via Jolt's `ApplyBuoyancyImpulse` (pieces kept awake so the drift never stalls), so severed limbs/heads bob off downstream; `Game::addBloodMark` drops marks inside the water footprint (blood washes away) and stream-bed debris impacts skip the smear/droplet burst. Ripple glints scroll +z matching the current; stone-lined banks, sakura trees dispersed through the playfield — upright, their trunks in the obstacle list, canopy/branch cosmetic — plus a leaning collider-free backdrop rank past the playable depth, looping fall of tumbling petals, and the **shinobi no ie** on the widened left flank: an authored `HouseBox` list — draw + colliders from one table — with a 0.36 m engawa platform fighters step onto (under the 0.4 m step-up), solid back/left walls, open front and right side, solid two-tier roof, flush cosmetic shoji screens). The picked level index rides in main's `matchLevel` (beside the loadout indices, so Rematch keeps the arena) and is baked into `Game` at construction (`Game::level()` — `drawScene` reads it, which also picks the diorama behind the menus).
- `src/weapons/` — the sword loadout armory, one file per blade (same shape as `src/characters/` and `src/levels/`): `weapon.hpp` the public surface (`WeaponStats`, `WeaponDef`, `kWeaponCount`, `weaponDef(index)`), `weapon.cpp` the index → def table (armory order = select-screen order = netplay index; append, never reorder), `registry.hpp` the per-blade namespace declarations, and one .cpp per weapon (`katana.cpp`, `wakizashi.cpp`, `odachi.cpp`) holding its `kDef` in designated-initializer form plus the note on what equipping it costs. Adding one: new .cpp, a namespace in `registry.hpp`, a row in `weapon.cpp`, `kWeaponCount`++. Weapons modify the wielder rather than replace their stats: `swingScale` multiplies windup/active/recovery, `reachBonus` adds meters of blade, `knockbackScale` multiplies shove dealt, `damage` scales the torso-hit and sever blood costs (never the beheading — the execution empties the pool with any blade), `bladeWidth` is a visual-only thickness cue (`SamuraiPose::bladeWidth`). Current three: Katana (neutral — all 1×, so character tuning is unchanged), Wakizashi (fast, short, cheap cuts), Odachi (slow, long, ruinous). A blade also carries a **stance** — `stance.hpp/.cpp`, lifted from Bushido Blade's three (High over the head, Normal pointed at the foe, Low trailing down and behind) and **one per weapon** for now, so choosing a sword chooses a style: Odachi High, Katana Normal, Wakizashi Low. A `StanceDef` is where the blade rests (`readyAngle`), where the guard holds it, and the `StanceArc` — start and end angle about the shoulder — of each of the three attacks, plus a small offense/defense trade (`damageScale`/`knockbackScale`, and `riposteScale` on the counter window the *defender* earns by catching a blow in it). Those angles are the reason this is its own leaf header rather than data inside `weapon.hpp`: **game.cpp sweeps the hit test along them and samurai.cpp animates the arm along them**, and the two reading one table is what keeps the cut landing where the blade is drawn. Normal's numbers are deliberately the tuning every attack had before stances existed, so the katana still plays exactly as it did and the other two read as departures. Cycling stances mid-match (Bushido Blade's Square button) is the obvious next step and nothing assumes one per weapon. `Game` bakes weapon into character once in its ctor; everything outside the sim (bot, rendering) reads the resolved numbers via `Game::stats(i)`, never the raw roster.
- `src/game.hpp/.cpp` — simulation: two `Player`s moving freely in the x/z ground plane. Gameplay stays authored (Game decides velocities: move speed, jump, gravity integration into `vy`, knockback — the per-fighter numbers come from each player's `CharacterDef` with their `WeaponDef` applied, both picked at select time); collision is delegated to `Physics` per fixed step, which returns resolved position + grounded. Sword combat: `AttackState` machine (windup → active → recovery, durations per character) crossed with an `AttackKind` (light / heavy / jab) picked at press time — `kAttackTuning` in game.cpp scales the wielder's resolved phase times, damage, knockback, and hitstun per kind. What the swing *looks* like is not there: the arc belongs to the **stance** the blade is carried in (`weapons/stance.hpp`, resolved per fighter by `Game::equip` and read back through `Game::stance(i)`), which is what makes an odachi's overhead cleave and a wakizashi's rising cut different swings rather than the same one at different speeds. The sweep mixes `StanceArc::start`→`end` and `swordArmAngle` in samurai.cpp mixes the identical pair, from the same table. The jab pierces instead of cutting: `canSever = false` downgrades any limb/head connect to a torso-grade hit — no dismemberment, no execution. **Blocking**: holding `PlayerInput::block` raises the guard (`Player::blocking`; needs an arm, standing, not mid-swing — the model holds the blade at the foe via `SamuraiPose::blocking`), scales walk speed by `kBlockMoveScale`, and suppresses attack presses. A blocked connect (any attack from the defender's front) costs no blood and can't sever — the defender takes a short `kBlockstunTime` stagger plus `kBlockKnockbackScale` of the shove, and a `Sfx::Block` clang plays. The catch opens a **riposte window** (`Player::riposteTime`, `kRiposteWindow` scaled by the caught attack's hitstunScale — heavier blows leave longer openings; the blocker's kimono glows gold while it's live, and a clean hit taken erases it): the first attack started inside it gets `kRiposteWindupScale` on its windup (`Player::attackWindupScale`, also folded into the pose's attackT). **Sprinting**: holding `PlayerInput::sprint` while actually travelling breaks the stance and runs (`Player::sprinting`; not out of a swing, hitstun, a crouch or a fall, and *not* on the control alone — a fighter standing still holding it has neither broken their stance nor any reason to be looking elsewhere). It scales move speed by `kSprintMoveScale` (2.2, so the Ronin's deliberate 0.85 m/s becomes a 1.87 m/s run — a number bounded by the legs rather than by feel: `kShuffleStride` is fixed by geometry, so a sprint buys speed as **cadence only**, and the walk's already-brisk ~3.1 foot movements a second scale straight with it. Past ~2.2 it reads as scurrying, and the honest fix is a second gait — feet crossing, a real stride, a lower hip — not a bigger multiplier) and takes away everything the stance was buying: no guard, no swing (a press made mid-sprint is not dropped, it waits on the existing `attackBuffer` and fires when the run ends), and a body turned the wrong way for either. That last part is the point rather than a side effect, and is why `Player::facing` — a ±1 mirror, which is the same thing as a yaw of 0 or π and nothing else — became **`Player::yaw`**, radians about +Y: a running fighter turns to face where they are *going* at `kSprintTurnRate` (12 rad/s), which is what makes movement in depth mean something, and is exactly why they cannot fight out of it — the blade is not pointed at anybody. Coming out of a run the body walks its yaw back to the foe at the same rate rather than snapping, so the instant flip a duel has always used is taken only from a body already square (the exact `yaw == 0 || yaw == kPi` test is asking precisely that, and those two values are the only ones ever written there; a body that has been *rolling* walks its yaw round the same way, which is the only thing that ever takes a downed fighter off the axis). **Rolling** is the same control and the same bargain for a fighter with **no legs at all**: a crawl is paced by the arms (`kCrawlSpeed`, a quarter of a walk at best and nothing whatever with no arms either), so the sprint control turns the body over instead (`Player::rolling`, gated on `Player::legless()` — both legs severed — and on the topple having finished, since mid-fall there is nothing to push against). It buys `kRollMoveScale` (0.7, so the Ronin's 0.85 m/s crawl-or-nothing becomes a 0.6 m/s roll) and costs the same as a sprint: no swing (the press waits on `attackBuffer`), and a body turned to where it is going. Two things make it a roll rather than a slide. The spin is about the model's **own +y**, the spine — `Player::rollSpin`, applied *inside* the topple (`spinLocal` before `rollLocal` in `modelToWorld`, matching drawSamurai's `Ry(yaw)·Rx(bodyRoll)·Ry(rollSpin)`), so the body turns about the long axis it is lying on instead of tipping over a second time, and every hurtbox comes round with it. And the rate is the shuffle's rule applied to a barrel: a planted foot must not slide, a rolling body must not skid, so the spin comes out of the ground covered — one radian per `kRollRadius` (0.30 m, the torso's own half-thickness) — rather than being a number of its own. The sign is `-fallSide` and is the whole of the geometry: tipped toward +z, a rising spin lifts the body's front, which is rolling *backwards*. Unlike the crawl it does not care how many arms are left, which is the point — a fighter reduced to a torso can still cross the arena for a dropped blade. `rollSpin` is not wound back when the roll ends: a body that came to rest face down stays there. Everything that read the mirror now reads the angle from one place — `yawLocal`/`modelToWorld` for the blade sweep and every hurtbox, `Player::forward()` for the shove direction and the guard's front (a dot product now, not a sign), `Player::sideAxis()` for the tumble a thrown blade takes, and `Player::lieOffset()` for where a toppled body actually lies (the blob shadow an unlit level falls back to, and the bot's depth steering) — because two copies of "which way is this body turned" would put the cut somewhere the fighter is not. **Crouching**: holding `PlayerInput::crouch` while grounded and upright ducks (`Player::crouching`; `Player::crouchAmount` chases it at `kCrouchRate` so the duck is a motion, not a snap): walk speed scales by `kCrouchMoveScale`, jumping is suppressed, and the whole upper body drops `kCrouchDrop` × amount — pose (samurai.cpp folds the legs, `SamuraiPose::crouch`), hurtboxes (`crouchedLimbBounds`: arm/head boxes drop, leg boxes squash toward the floor; torso box drops too), and the attacker's blade pivot all move together, so a crouched fighter is genuinely smaller and crouch-swings sweep a lower, leg-hunting lane. The physics capsule is unchanged (nothing overhead to duck under; body-blocking stays full height). Attack presses are buffered (`Player::attackBuffer`, `kAttackBufferTime`) so a click during blockstun/hitstun/recovery fires on the first able tick instead of dropping — which is what makes the riposte clickable at the clang. During active the blade is swept as a segment along the attack's arc (pure math on `Player::pos`, not Jolt queries) against per-limb AABBs (`samuraiLimbBounds` + per-limb pad) and a torso box. Any connect ⇒ hitstun + planar knockback + upward pop + interrupts the victim's swing; a limb connect also **dismembers**: the limb is flagged in `Player::severed[]`, launched as a Jolt debris body (`SeveredPiece` list, drawn by main), and stays lost for the match. The head's z pad is tight so beheading takes depth-aligning the blade lane (sword arm rides `kShoulderSide` off center); losing the sword arm swaps the katana to the off hand, losing both arms disables attacking. **Hopping**: losing *one* leg no longer costs the footing. It used to — the body toppled on the first leg taken, and since that is also the easiest limb to reach, the first cut very nearly settled the match. But there is still a leg under them, and standing is what a duel is, so they stay up and hop on it (`Player::hopping()` — exactly one leg gone and alive; `kHopMoveScale` 0.55, so the Ronin's 0.85 m/s becomes 0.47). The cost is the leg's and no more: no sprint and no jump (a run is two legs alternating and a leap wants one to spare), but the guard, the swing and the crouch are all still theirs. The gait is `hopCycle` in samurai.hpp, and it keeps the shuffle's one rule for the shuffle's one reason — **the foot on the floor must not slide** — by covering all of its ground in the air: the surge is flat zero through the plant and a bell through the flight, averaging to exactly 1 over the cycle the way `2·sin²` does, so game.cpp's speed curve and the model's foot are again one function. It is also where the body's *rise* comes from, which is why the hop is not left to the renderer: `bodyRiseY` folds it in with the crouch drop, and every sim height above the legs — shoulder pivot, torso box, arm and head hurtboxes, the hand a thrown blade leaves from — rides that one number, so a hopping fighter is hit where they are drawn at the top of a hop as well as the bottom. **Toppling** is then what losing the *last* leg costs (or dying): the body tips about the feet toward the side it went from as an inverted pendulum (`Player::fallSide`/`fallTilt`, rendered via `SamuraiPose::bodyRoll`) until it lies on the floor (thud + blood smear). `Player::downed()` is that state and only that state — dead or `legless()` — which is what the crawl, the roll, the prone capsule and the bot's finishing crouch all key off, and every one of them means the same thing by it. Downed fighters can't jump, crawl at a fraction of move speed set by remaining arms (`kCrawlSpeed`), and can still swing — all hit-test geometry (blade pivot/arc, limb and torso boxes) is transformed by each body's roll via `modelToWorld`/`rollLocal`/`rollHalfExtent`, so a prone chop becomes a ground sweep and a prone defender is hit where they lie. When the yaw flips while down, `fallSide` negates too so the world-space lie direction is preserved. `Physics::setCharacterProne` swaps the capsule to a squat one so opponents can step over the body. **Blood**: every connect bursts ballistic `BloodParticle` droplets from the wound (pure math, no Jolt; bigger burst on dismember); a droplet reaching the ground — or a debris impact near y = 0 from `debrisImpacts()` — stamps a `BloodMark` floor splat (capped ring buffer, oldest recycled; marks carry per-mark y jitter + random yaw, reaching y = 0.022, and main draws them under the fighters' shadows — which is placed against that number rather than guessed, since a stain nearer the camera than a shadow crossing it would punch holes straight through it). **Dropping and taking up a blade**: `PlayerInput::drop` is one edge-triggered control meaning both halves of the same idea — throw the sword down if there is one in hand, otherwise take up the nearest one within `Game::kPickupRange` (1.25 m in the ground plane) that has finished settling. Which of the two it means is decided **in the sim**, since nothing outside it knows what a fighter is holding, and after the first exchange that may not be the blade they picked. So `Player::weapon` is per-fighter *state* (an armory index, or `kUnarmed`) rather than part of the match setup, and `Game::equip` is the one place `m_weapons`/`m_stats` are written — everything downstream keeps reading `stats(i)` and a fighter who takes up an odachi swings like one. Empty-handed there is no attack **and no guard** (it takes crossed steel to catch a cut), which makes throwing the sword away the most expensive thing a fighter can do to themselves; losing **both arms** drops it whether its owner wanted to or not. A thrown blade is a `DroppedWeapon` — a Jolt debris body on exactly the same terms as a severed limb, so it tumbles, gets kicked around and floats downstream for free, and lands inside `checksum()` for free with it. It belongs to nobody once it lands, which is the whole point: either fighter can take it, and it is the same shape a blade the *level* places will need. One thing this cost: `debrisImpacts()` had to start saying **which** body it came from (`Physics::DebrisImpact::id`, carried in the body's Jolt user data), because a sword hitting the floor must clatter without leaving a blood smear. **Blood (the win condition)**: each fighter has a `Player::blood` pool (max 100). Costs are deliberately stingy (torso hit 3, severed limb 8, stumps drain 0.25/s each) so attrition is slow background pressure — **beheading is the intended execution** and empties the pool instantly; a limbless fighter does bleed out eventually, but you're meant to finish them. Empty = dead: the corpse collapses through the existing topple path (`Game::collapse` seeds `fallSide` if still standing), takes no further input, and `Game::winner()`/`over()`/`overTime()` expose the outcome (decided once — post-match deaths, e.g. the winner bleeding out or corpse chops, can't flip it; corpses can still be dismembered). **The clock is the other way a match ends**: `m_timeLeft` counts down from `kMatchTimeLimit` (99 s) while the duel is live, and `decideOnTime` hands it to whoever is in better shape — blood, then limbs still attached, then, only if the two are identical to the bit, fighter 0. That last tie-break is arbitrary and meant to be: it can only be reached when nothing happened for ninety-nine seconds, and a *draw* would be a whole third outcome for the win overlay, the rematch flow and netplay's level ownership to learn for that one case. Nobody is killed by the bell — both fighters are left standing exactly as they were, and only a swing in flight is cut short so the overlay doesn't come up over a blade frozen mid-arc (`Game::timedOut()` is what makes the overlay say *left standing* instead of *takes the duel*). The clock is advanced **after** the rest of the step, so a kill landed on the same step is what decided the match rather than the expiry alongside it, and it is hashed like any other sim state: two peers disagreeing about it by one step would end the duel differently. Attack input is edge-triggered and latched outside the sim so presses aren't lost between fixed steps (see `src/input.hpp`; GLFW sticky input modes are on for the same reason). **Two rng streams, deliberately**: `m_rng` decides what the fight turns on (which way a dying body topples — the only sim roll there is), `m_cosmeticRng` decides only how blood looks. Splitting them keeps the number of droplets a hit happened to spawn from shifting every later gameplay roll, and is what will let a rollback layer leave cosmetic state out of save/restore; retrofitting the split later would move every roll in the game. `Game::checksum()` is FNV-1a over everything the sim decided — both `Player`s field by field, both rng words, the outcome, and every debris body's position/orientation/velocity — hashing floats **by their bits**, since bit-exactness is the point and `0.0f == -0.0f` would hide a real divergence. The blood particles and marks themselves are left out: they're a pure function of `m_cosmeticRng`, which *is* hashed, one word standing in for thousands. It's walked only when the replay harness is on, so a normal match never pays for it.
- `src/bot.hpp/.cpp` — enemy AI: a `Bot` outside the sim that reads the public `Game` state each fixed step and emits a `PlayerInput` for the fighter it was told it drives (main calls `bot.think` inside the fixed-step loop, and re-seeds it per match against whichever slot `matchSources` hands it — player 2 today). Mode machine re-rolled every ~0.25–0.7 s (approach 60% / strafe 25% / retreat 15%): holds a strike band scaled off its own reach stat, steers into the foe's depth lane (strafing jinks instead), occasionally hops in from range, and reacts to a foe windup in range with a ~25% chance to raise its guard (holds block ~0.3–0.6 s) or ~30% to back off. A successful catch drops its guard and counters immediately — the riposte window bypasses its attack cooldown. **Sprints across the long part of an approach** — only in `Approach` mode and only past `reach·kBandHi + kSprintRange`, since a sprint turns the body away and throws the guard with it, so it is a way of crossing the arena and never a way of arriving; the margin is what puts it back in its stance well before anything can reach it. A disarmed bot runs for the blade too (`kSprintRange` from it), where the trade is free: it has no guard or swing to give up. Swings when lined up, gated by a randomized 0.35–1.1 s cooldown — the cooldown is the difficulty knob. Mostly light attacks; commits to the heavy mainly when the foe is in hitstun or downed (rare greedy read otherwise) and jabs when uncomfortably close. Against a **downed** foe in striking range it also **crouches**: the blade pivots at the shoulder, so a standing swing sweeps a lane a toppled fighter lies clean under, and a bot that keeps chopping the air over a body is how a match ends on the clock instead of with a kill (the `--auto` fixture ran 1428 steps before this and 639 after). Only in range — the duck costs more than half the walk speed and reaches full depth in ~0.1 s, so there is nothing to gain by starting it sooner. Its depth steering aims at where a body **lies** rather than at its capsule (`lieZ`: the topple rolls the model about the local +x axis at the feet, so a prone torso swings ~0.9 m off `pos.z` and the head half again as far — the same math main stretches the fallback blob shadow by), applied to *both* fighters, since a downed bot's own shoulder has swung just as far out of line. Upright, `sin(0)` is 0 and it is exactly what it was; downed, it is the difference between finishing and flailing — on the one fixture that loses a leg mid-match, 5250 steps and a win by bleed-out with all four limbs taken became 730 steps and a beheading. Its depth steering runs through `quantizeAxis` — the bot only gets to press what a player could press, since an analog lean is an input no recording or netplay peer can carry. **Being empty-handed overrides everything else on that page**: with no blade there is no attack and no guard, so a disarmed bot walks to the nearest `droppedWeapon` and presses drop once inside `kGrabRange` (0.75 m, deliberately well inside `Game::kPickupRange` so the press always lands rather than the bot stopping short of a sword forever). Without it a disarmed bot walks into sweeps it cannot answer until somebody runs out of blood, which between two disarmed fighters is never. The branch is gated on the bot **having an arm** and on there being something on the ground, and the arm guard is not theoretical: the usual way a bot ends up empty-handed is losing *both arms*, which is precisely the state `takeUpWeapon` refuses — ungated, it walks to the sword it just dropped and stands over it pressing take-up for the rest of the match, which is worse than what the branch exists to fix. Failing either guard it falls through to the ordinary mode machine and stays in the fight while its stumps bleed it out.
- `src/physics.hpp/.cpp` — Jolt wrapper (pimpl; Jolt headers only in the .cpp). Owns the `PhysicsSystem`, invisible static arena colliders (ground + 4 walls — side walls placed at the ctor's per-level `arenaHalfWidth`, depth fixed; the ground is one flat slab unless the ctor gets per-level `groundBoxes` (Hanami's carved stream channel); these replaced the old position clamp — plus any per-level `StaticBox` obstacles, e.g. Hanami's stones/trunks/house; same layer as the arena so fighters and debris collide with them), an optional `Water` volume (per-step buoyancy/drag/current on debris via `ApplyBuoyancyImpulse` before the world update), and one `CharacterVirtual` capsule per fighter (radius = `kHalfWidth`, height = 2·`kHalfHeight`, origin at the feet; `Player::pos` is capsule pos + half height in y). Fighter-vs-fighter solidity comes from `CharacterVsCharacterCollisionSimple`. `moveCharacter` does `SetLinearVelocity` + `ExtendedUpdate`; `step` runs the rigid-body world (arena statics + severed-limb debris boxes; a `DEBRIS` object layer collides with the world, other debris, and the fighters — the `CharacterVirtual` update shoves the much lighter limb bodies aside, so players kick severed pieces around by walking into them). A `ContactListener` (mutex-guarded — Jolt calls it from job threads) records debris contacts above a 2 m/s closing-speed threshold; `debrisImpacts()` exposes them (contact point, closing speed, **and which debris body it was**) per step and Game turns them into thud sound cues and, for ground contacts *from a limb*, blood smears — the handle rides in the body's Jolt user data, which is all a contact callback has to work with, and is what keeps a thrown-down sword from bleeding on the floor. `removeDebris` destroys a body (a blade being taken back up) but **retires** the handle rather than reusing it: every handle already issued has to keep meaning the same body, so the slot stays as a hole that `step`/`debrisStates` skip. The job system is **`JobSystemSingleThreaded`, on purpose**: Jolt only promises determinism for the same binary at the same thread count, and a pool sized from `hardware_concurrency()` — which is what this used to be — is precisely the thing that differs between two machines trying to run the same match. The sim is two capsules and a handful of limb boxes; a pool wins nothing here. `debrisStates()` exposes every debris body's raw position/orientation/velocity for `Game::checksum()`, because the rigid-body world sits **inside** the determinism boundary even though no limb decides a fight: a piece landing one step late changes the `debrisImpacts()` stream, which becomes blood marks, which advances an rng. Jolt is pinned at v5.6.0, dynamic CRT, demos/tests off (see CMakeLists).
- `src/audio.hpp/.cpp` — miniaudio wrapper (pimpl, same pattern as Physics; falls back to silent if no device). Startup is **staged rather than done in the constructor** — `initDevice`, `initSfx`, then `initVoices` — so the loading screen can run it a piece at a time and report honest progress (main's `LoadStep` table drives them in order). The constructor costs nothing; `play` is a silent no-op until `initVoices` lands, exactly as it is for the whole run when the device didn't open. All SFX PCM is **synthesized at startup** (no asset files): swing whoosh (bandpassed noise, swell timed so it peaks as the blade goes active), hit (pitch-dropping thud + crack), dismember (deeper thud + slice band), thud (severed limb landing; dull, no crack). Event flow: `Game::update` pushes `SoundCue{Sfx, x, gain}` into a list (swing on attack start, hit/dismember on connect, thud from `Physics::debrisImpacts()` with gain scaled by impact speed); main drains it once per render frame via `soundCues()`/`clearSoundCues()`, panning by world x against the fighters' midpoint and adding per-play pitch jitter. Each effect has a small round-robin voice pool (own `ma_audio_buffer` cursors over shared PCM) so overlapping plays don't cut each other off. **Music**, unlike the effects, is **files**: three seamless loop tracks (`Music::Menu` plus one per battleground, ordered after Menu to match the level roster — `levelMusic(levelIndex)` maps index → track) live as WAVs in `assets/music/`, named by `kMusicFiles` in the header. `loadMusic(track)` decodes one in full (~3–4 ms; no `MA_SOUND_FLAG_STREAM`, so playback never touches the disk again) and is **idempotent**, so callers just say what they need and a track loaded once stays loaded — main asks for `Menu` from the load-step table and for the battleground's from `startMatch`, which is what makes a level's theme arrive with its level instead of costing every launch. A track that fails to load is never retried (no per-frame re-open or re-log) and costs only itself; the game plays on. The mixer levels may be set at any point — `setMusicVolume` stores the level either way and seats it on tracks as they load — so loading the player's settings needn't come before any of it. Composition lives in `tools/musicgen.cpp` (see below), not here. **Mixer levels** come from the player's settings via `setMusicVolume`/`setSfxVolume` (0..1, 1 = as authored): music is pushed to every loaded track's bus volume at once — which in miniaudio is a *separate multiplier* from the crossfade fader, so setting it mid-transition scales the fade instead of cancelling it — while SFX is applied per effect as `play` starts it. `Audio::playMusic(track)` is an idempotent "this should be the music now" (no-op if already playing, else ~0.7/0.9 s crossfade via miniaudio sound fades) — main calls it once per frame keyed off `AppState` (front-end ⇒ Menu theme, match ⇒ `levelMusic(game->level())`), so transitions fall out of state changes; Rematch keeps the track running uninterrupted. miniaudio is pinned at 0.11.23 with `MINIAUDIO_NO_EXTRA_NODES`.
- `src/camera.hpp/.cpp` — `FramingCamera`: follows the fighters' midpoint, zooms out so both always fit the frustum (with margin), accounting for each fighter's depth; exponential smoothing. `position()`/`target()` expose where it has settled, which is what the intro sequences ease their own shots *into* — two viewpoints interpolate and two view matrices do not.
- `src/intro.hpp/.cpp` — the two arcade intros, and the one thing they have in common: both take the camera away for a few seconds and hand it back. A `CameraShot` (eye + target) is all either gets to say — the projection stays `FramingCamera::proj` throughout, so a sequence can change the viewpoint and never the lens, and an intro that quietly widened the fov would hand the match back through a zoom. Both also ease their last shot into where the framing camera has settled, so the handover is the end of a camera move rather than a cut. **`VersusIntro`** is the pre-match card: a close-up on each fighter in turn (built from `Player::forward()`, not world axes, so it stays a close-up whatever a future level does with the spawns) with a slanted name plate slamming in beside them, a pull-back to the shot the match will be played from, then FIGHT! It runs **inside `AppState::Playing`** rather than as a state of its own, because a match under an intro is still a match — Esc leaves it, a peer is still connected, the win overlay still cannot fire — and every one of those would need saying twice for a fourth state. What it actually needs is one question answered for the fixed-step loop: `holdingSim()`. That freeze is **not a pause** — nothing is banked — and for a netplay peer it is precisely the stall lockstep sits through whenever an input has not arrived, so two peers holding their own copies need not agree on anything and cannot desync over it. `--auto` and `--replay` never begin it: a fixture and a log both want the match to be exactly the steps they describe. The banner deliberately **outlives** the freeze, since FIGHT! belongs over a fight. **`TitleIntro`** is the attract sequence, played once between the loading screen and the menu: two fighters charge, trade a blow, and the logo lands on the clash. The duel is **real rather than posed** — the sequence emits ordinary `PlayerInput`s and the diorama simulates them, so the swing has the windup it has in a match and the block rings with the same clang; a pose table would only have been a second, worse copy of the animation the model already does. Its clock advances **only inside the fixed step** (which is why the inputs and the clock are one `step(dt, out[2])` call — an attack is a single-step press, and a caller free to ask twice would fire it twice), so the sequence is step-exact and plays out identically every launch. The fight beats are timed against the Ronin's heavy — 0.12 s of windup scaled by 1.9, then 0.14 s scaled by 1.25 of active — because the guard has to be up across the **whole** of that active window, not just its start: releasing it early is not a near miss, the blade lands unblocked, and the first cut of this sequence took the Shinobi's leg off and left him lying behind the main menu. The counter is a **jab**, which cannot sever (game.hpp), so between the caught heavy and the thrust the exchange is *guaranteed* to leave both fighters with all four limbs. That guarantee is load-bearing: the script settles both back into their guard before the end and the diorama is then **left exactly as the duel finished it**, blood and all, rather than rebuilt — which is a better menu backdrop than the spawn pose it replaced, and costs nothing. Both sequences are skippable by any bindable control, and both **arm on release** exactly the way the options screen's rebind capture does — the click that picks the battleground is still held when the match is built, so a skip taken on the level alone would mean nobody ever saw the versus screen. Esc goes straight to `skip()` instead, since it is unbindable and so can never be a control left held over from the screen before. One rule worth keeping: `stampText` bakes at a **fixed** font size and scales the emitted *vertices*, never the size it hands ImGui. ImGui bakes a fresh set of glyphs for every distinct size asked for, so a stamp animating from 530 px down to 190 px asks for a few hundred full-size bakes in as many frames — the atlas grows without bound and the game stops dead. It did exactly that the first time this was written, and the symptom is a hard lockup rather than a slowdown.
- `src/renderer.hpp/.cpp` — all Vulkan state; API is `beginFrame` / `setViewProj` / `drawBox(model, color)` / `endFrame`. Also owns the Dear ImGui integration (context + GLFW/Vulkan backends, dynamic rendering path, own small descriptor pool): `beginFrame` starts an ImGui frame, `endFrame` records the draw data before `vkCmdEndRendering`, so callers just emit ImGui widgets between the two. ImGui is pinned at v1.92.1, built as a static lib from FetchContent sources (no upstream CMake); `imgui.ini` persistence is disabled.
- `src/samurai.hpp/.cpp` — procedural samurai model: ~29 boxes (hakama legs, kimono torso, obi, sode, arms, head, kasa, sheathed katana) with stride/idle/jump animation driven by `SamuraiPose`. Each **leg is a two-bone chain** — thigh, kneecap, shin — but it is **not posed; it is solved**. The feet are placed where the shuffle says they go and the joint angles come back out of them: equal-length bones make the leg an isosceles triangle, so the knee closes by `2·acos(reach/kLegLength)` and the thigh sits half that angle off the straight hip-to-foot line. Swinging a leg from the hip instead gives exactly one way to reach the ground, which is not enough freedom to hold a stance *and* keep both feet on the floor. That constraint is also why the guard is crouched at all: a leg is a fixed-length lever, so a hip at full standing height can only reach the floor straight down, and holding the feet any distance apart requires settling onto bent knees. **`kStanceHipY` (0.70), `kStanceSep` (0.34) and `kShuffleStride` (0.55) are locked together by that** — widen the stance or lengthen the step and the hip has to come down to keep both feet planted; measured, the planted foot slides <0.1 mm in any valid combination. Cadence is the price: small steps at a fixed speed means frequent steps, ~3.1 foot movements/s at the Ronin's 0.85 m/s, and *speed* is the only lever that makes it stately. There is deliberately **no stride bob** — a shuffle holds its height, which is most of why it reads as a fighter rather than a person walking. `SamuraiPose::strideBlend` closes the stepping (and the foot lift with it, or a fighter stopping mid-cycle stands there holding one foot in the air) while the stance separation is held either way. The knee is placed with a **pole vector**, not by solving in the plane through hip and foot: with both ends fixed the knee can sit anywhere on a circle about the hip-to-foot axis, and the pole — model forward, always — is what picks the point. Solving in-plane bulges the knee toward whichever way the foot happens to be offset, which looked fine on the lead leg by luck and folded the rear leg backward at the knee like a horse's hock. A consequence worth knowing: the leg is then not confined to any one plane, so there is no pair of Euler angles to write and the bones are placed straight from the joint positions (`boneXf`). **`shuffleLeg` is the single solve both ends read** — samurai.cpp draws the leg from it and game.cpp bounds the leg from it — which is the same contract stances keep, and for the same reason: two copies would drift and the fighter would be hit where their legs are not. `hopCycle` is the second gait under exactly that contract, for the one leg a fighter with the other one cut off is standing on; both go through the same `solveLeg`, so the knee is picked the same way whichever gait placed the foot. It returns the joint angles *and* the joint positions, so `crouchedLimbBounds` builds the leg hurtbox as the AABB over hip/knee/foot plus limb thickness. A static box cannot do that job here: the same leg sits 0.17 m off center in the guard and 0.45 m out at full extension, so one box either misses the extended leg or swallows a standing fighter whole. It also means the crouch no longer needs mirroring into the leg hurtboxes at all — it lowers the hip, the legs re-solve for the feet they were already on, and the bounds follow for free. The stance sits the whole body `kStanceDrop` (0.15 m) below `kHipPivotY`, and **every sim height is authored as its standing-tall value minus that** — `kShoulderHeight`, `kHandHeight`, `kTorsoCenterY`, and the arm/head centers in `samuraiLimbBounds` — since otherwise the blade sweeps 15 cm above where it is drawn and the head you aim at is not the head you must hit. The physics capsule is deliberately *not* dropped: it is a collision volume for body-blocking, not a hurtbox. `SamuraiPose::stance` (from `Game::stance(i)`, i.e. from the blade in hand) is what the sword arm follows: `swordArmAngle` raises out of the stance's ready angle, carries the blade through that stance's arc for the attack, and settles back to ready, while a raised guard holds it at the stance's `guardAngle`. Those are the very numbers game.cpp sweeps the hit test along — the model is not free to interpret them. Severable parts are indexed 0..4 (arm +z, arm −z, leg +z, leg −z, head; must match game.hpp's `Limb`): `SamuraiPose::severed` draws stumps instead, `samuraiLimbBounds` exposes each limb's local AABB (gameplay hit regions + debris shapes), `drawSeveredLimb` draws a detached limb under a rigid-body transform. An armed fighter carries the blade **drawn for the whole match**, held at the stance's `readyAngle` whenever they are doing nothing else with it — which is what makes a stance something you read off a fighter standing there instead of a shape that exists for the third of a second a swing takes, and costs the sword arm its stride swing (nobody walks a sword around like an empty hand). That moved the "nothing to swing" cue: `SamuraiPose::armed` now takes the sword off the model entirely and gives the arm its swing back, and the **empty hand** is what says so — much louder than the old tell, which was a 5 cm grip missing from the hip. The saya stays on the belt and is always empty, since the blade that belongs in it is in the fighter's hand. `drawDroppedBlade` draws a blade as a free object under a rigid-body transform (same contract as `drawSeveredLimb`), sized by `bladeSteelLength(reachBonus)` — from the *weapon* alone, never a fighter's reach, because a blade on the ground is the same object whoever picks it up and one that grew as it changed hands would be lying about what the next swing covers. **`drawSamuraiShadow`** prints the fighter on the floor under the level's own sun (`levels::sunShadowBox`), which is what a disc at the feet could never do: the shadow holds the stance, takes the step, ducks, swings the blade and lies down with the body. It is the same walk of the body the drawing is — `buildSamurai` is one function emitting every box to a sink, and drawing and casting are two sinks over it, for exactly the reason `shuffleLeg` is one function with two readers. A second description of the fighter would drift from this one, and a shadow is the most literal way that drift could ever show. Boxes lying wholly inside another's silhouette (kneecap in its thigh, head under its kasa, obi in the hip skirt) carry a `detail` flag the drawing ignores and the shadow skips, which leaves **ten** casters: two thighs, two shins, hip skirt, torso, two arms, the blade, and the kasa's brim. Those ten are emitted **top down** into a thin band under y = 0.03, and the depth write is what makes them one silhouette rather than a heap: where two overlap the higher wins and the lower is rejected outright, so nothing double-darkens at a joint. The band is placed against the blood marks' 0.022 below it, and it costs nothing to be generous with the spacing — the camera looks *level* rather than down, so a millimetre of lift is a fraction of a percent of screen height, not the slide across the ground it would be in a top-down game. Softness and darkness come off the *body's* height, not each box's, since a samurai is not a tree and grading the parts separately would smudge the kasa while the sandals stayed crisp — so a fighter in the air throws one wide faint shadow well off to the side, which is how you read where they are going to land. A fighter also prints half again as hard as the scenery around them (`kShadowWeight`, clamped): the level's `shadow` is the strength of a thing standing in the battleground, and the two people fighting in it are what the eye is tracking — at scenery strength it was there on Hanami's grass and not readable, which is the one job it cannot fail at. An unlit stage (Dojo, `sun.shadow` 0) casts nothing and gets main's blob instead, which was never lighting: it is what makes depth readable in the air, and that is owed whatever the sky is doing
- `src/synth.hpp` — the DSP primitives shared by everything procedurally generated: seeded `noise`, a Chamberlin `Bandpass`, `normalizePeak`. Header-only, and the one thing `audio.cpp` and `tools/musicgen.cpp` have in common.
- `tools/musicgen.cpp` — a standalone exe that renders `assets/music/*.wav`. The music is still *composed in code* (the note tables, the koto/taiko/bell/flute voices, the wraparound loop seam), but it's authored here and rendered ahead of time rather than re-synthesized on every launch, which is what the three tracks used to cost: ~292 ms of a ~325 ms load, producing identical PCM every run. It's built with everything else so it can't rot, but **nothing depends on its output at build time** — run `build\musicgen.exe` by hand after changing a track (optional argument: an output directory other than `assets/music`). Deterministic end to end (seeded rng, no clock), so re-rendering an unchanged track rewrites the same bytes and git stays quiet. Adding a track: a render function, a row in `kRenderers`, and the matching `Music` enumerator + `kMusicFiles` name in `src/audio.hpp`.
- `assets/music/` — the three rendered loops (`menu.wav`, `dojo.wav`, `hanami.wav`; mono 16-bit PCM at 48 kHz, ~6.6 MB total, committed). Normalized to a peak of 0.30 — that headroom *is* the game's music level, since a music volume of 1 means "as rendered". Real recordings could replace these tomorrow without the game knowing.
- `shaders/` — GLSL, compiled to SPIR-V at build time by glslc into `build/shaders/`

## Current conventions (early, expected to change)

- World space: x right, y **up**, z toward the camera, ground surface at y = 0, units ~meters. Camera looks down -Z from +Z; gameplay is side-focused but movement is full 3D.
- GLM is compiled with `GLM_FORCE_DEPTH_ZERO_TO_ONE` + `GLM_FORCE_RADIANS`; `FramingCamera::proj` flips Y for Vulkan clip space.
- Everything renders as a shaded unit cube generated in the vertex shader from `gl_VertexIndex`; models may rotate (normal matrix travels in push constants). `ObjectPush` is exactly 128 bytes — the guaranteed push-constant minimum — and must match `shaders/cube.vert`; do not grow it. `drawBox`'s **`unlit`** flag rides in `normal0.w`, which the normal matrix's columns leave spare, precisely because the block is full and a field of its own would push it over: it drops the diffuse term and emits the color as authored. Only the sky wants that — the shell and the clouds hanging in it — and it is not a style choice: a sky is a light source rather than a surface, and shading it would paint the four walls of one gradient band four different colors, and make a cloud's color depend on which side of the ring it had drifted round to.
- Depth: single D32 depth image shared by frames in flight, transitioned from UNDEFINED each frame.
- Shaders and assets are found through `src/paths.hpp` (`shaderPath`/`assetPath`), which checks **beside the exe first** and falls back to the `SHADER_DIR`/`ASSET_DIR` compile definitions. Those are absolute paths into the build and source trees, which is why a build could not previously be handed to anyone: the copy looked for its shaders where they had been on the machine that compiled them, and died before the window opened. Now a packaged build carries `shaders/` and `assets/` beside the exe and is self-contained, while a dev build finds the source tree and needs nothing copied after a compile — so editing a WAV still takes effect without a rebuild. Both roots are logged once at startup, since "no music and no idea why" on someone else's machine is otherwise unanswerable.
- `src/` is on the include path, so headers are included relative to it (`"game.hpp"`, `"levels/level.hpp"`) — no `../` paths from subdirectories.
